# Spec: Panoply kit migration (old layout → docs/agents)

- **Status:** implemented 2026-10-29
- **Plan:** `plan.md` in this folder

## Goal

Fonto's written rules and gates were on the kit's old layout: rule text under `.claude/rules/`, the
docs spine under `docs/claude/`, and a repo-generated `scripts/sync-agents.sh` that predates the
current kit. The current kit reads and writes `docs/agents/` + `.agents/rules/`, and its doctor
(`scripts/panoply.sh`) refuses to certify a repo it cannot judge. Two things were broken by that gap,
and both are observable:

1. **The agent gate refused edits.** The Hermes-side Panoply gate found no kit in this repo, so it
   reported "no kit source reachable" and blocked `write_file`/`patch` — every agent had to route
   around the gate through a shell, which is exactly the workaround the gate exists to prevent.
2. **The docs spine was unenforced.** `docs/claude/` held only two feature folders; the roadmap,
   in-progress queue, and architecture notes that `AGENTS.md` told every agent to read did not exist
   at all, so the "read in this order" contract pointed at nothing.

The user of this change is an agent (or a person) opening the repo cold: after it ships, the repo
tells the truth about where its plans live and the gates that enforce them actually run in CI.

## User stories

### US-1 — A cold agent finds one home for the rules (P1)

**Independent test:** clone the repo, read `AGENTS.md` top to bottom, and open every path it names.
Every path resolves, and no rule text exists in two places.

### US-2 — The kit certifies the repo (P1)

**Independent test:** `sh scripts/panoply.sh check` exits 0 in a fresh clone.

### US-3 — The gates run where they cannot be skipped (P1)

**Independent test:** a PR that changes code without a worklog line, or adds a plan outside
`docs/agents/<area>/<feature>/`, fails `verify` on the PR — not on a developer's machine.

### US-4 — Nothing that existed before the migration is lost (P2)

**Independent test:** `git log --follow docs/agents/architecture/gate/plan.md` reaches the pre-migration
file; the old `.claude/rules/*.md` bodies survive at `.agents/rules/*.md` with their project adaptation
intact.

## Edge cases

- A rule module the adopter adapted by hand must not be overwritten by the kit template — `apply`
  reports `KEPT` and the adapted text wins.
- A script the adopter diverged (`check-docs.sh`, `sync-agents.sh`, `check-expert-review.sh`) must be
  refreshed deliberately (`--force-scripts`) with a `.panoply-bak` backup, never silently.
- A repo with **no** doctor at all must still be migratable — today `migrate` aborts when it tries to
  back up a `scripts/panoply.sh` that does not exist (see the plan's findings).
- `AGENTS.md` carries project-specific facts (the Next.js version warning, the credential rule) that
  the kit template cannot know; the template is a base to merge into, never a replacement.

## Requirements

- **FR-001**: The repository MUST carry the current kit's doctor at `scripts/panoply.sh` and report
  `panoply: OK` (exit 0) from a clean clone.
- **FR-002**: Every rule module MUST live at `.agents/rules/<name>.md`; the generated mirrors
  (`CLAUDE.md`, `.cursor/rules/*.mdc`, `.clinerules/`, `.windsurf/rules/`, `GEMINI.md`,
  `CONVENTIONS.md`, `.github/copilot-instructions.md`) MUST be regenerated by `scripts/sync-agents.sh`
  and MUST NOT be hand-edited.
- **FR-003**: Every plan doc MUST live at `docs/agents/<area>/<feature>/plan.md` with a row in
  `docs/agents/roadmap.md`, enforced by `scripts/check-plan-home.sh`.
- **FR-004**: `AGENTS.md` MUST be the canonical hub: project facts, the onboarding order, and an index
  of the rule modules — not a second copy of the rule bodies.
- **FR-005**: The migration MUST NOT delete a pre-existing file. Files it supersedes stay until the
  owner removes them.
- **FR-006**: The landing gates MUST run in `verify.yml` so a non-agent contributor cannot skip them.
- **FR-007**: A change to code MUST NOT land without a worklog line in the same change
  (`scripts/check-docs.sh`), and a structural change MUST carry a spec and a plan with a
  `Deletion candidates` section (`scripts/check-spec.sh`, `scripts/check-algorithm.sh`).

## Success criteria

- `sh scripts/panoply.sh check` → exit 0 (measured: `panoply: OK — kit unreleased applied and current`).
- `sh scripts/sync-agents.sh --check` → in sync.
- `sh scripts/check-docs.sh --since origin/main`, `check-plan-home.sh`, `check-spec.sh`,
  `check-algorithm.sh --since origin/main`, `check-conflict-markers.sh`, `check-comments.sh` → each
  exit 0.
- `pnpm typecheck && pnpm lint && pnpm arch && pnpm conformance && pnpm test` → green, unchanged test
  count from the base commit (this change moves documents, not code).
- CI `verify` green on the PR, with the docs gates as steps in it.

## Assumptions

- The kit source is reachable at `/opt/data/panoply-kit` on the box where the migration runs, and CI
  does not need it: the doctor is copied into the repo, and `check` compares against the repo's own
  stamp, so an offline CI run still certifies the repo's state.
- `docs/claude/` and `.claude/rules/` are removed by the owner after review, not by this change.

## Domain & outside experts

Internal governance tooling for AI-agent repositories. No outside domain expert was consulted and none
is named here — inventing one would be the exact defect this kit's `claims.md` forbids. The evidence
behind the requirements is empirical: the gate's block messages, the doctor's exit codes, and the
divergence between the old `sync-agents.sh` and the current kit's.

## Open questions

None. Every requirement above is testable and was tested; the two items that could not be completed
inside the repo (deleting the old trees; refreshing the kit's own `migrate` defect) are recorded in the
plan as out-of-scope with their owner.
